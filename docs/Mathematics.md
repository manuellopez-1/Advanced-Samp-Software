# Mathematics Mode

Mathematics mode is a standalone post-processing step, invoked with `./AdSamp Mathematics <type> ...` (generated by the login's Mathematics branch — see [Login Mode](#login-mode)). It doesn't run any MD; it only reads already-completed FFS colvar/success/failure output and does numerical analysis on it. There are two calculations:

| Type | Function | Purpose |
|---|---|---|
| 0 | `FreeEnergyCalculation` | Reconstructs the 1D free energy profile along the order parameter from a full FFS milestoning run. |
| 1 | `LandscapeVariances` | Reports transition-probability statistics and a between/within-configuration variance breakdown for each FFS step. |

Both read the same on-disk conventions as the rest of the pipeline: per-trajectory colvar files prefixed `C` in each step's postprocessed directory, and `successes.txt`/`failures.txt` listing which initial configurations succeeded or failed at each step (see [OutputFiles](/docs/outputfiles.md)).

---

## Free Energy Calculation (`FreeEnergyCalculation`)

### What it does

Given the postprocessed directory for each FFS step and the milestone positions (λ_B, λ_1, λ_2, … λ_goal) that bound them, this reconstructs a free energy profile *F(λ)* across the whole reaction coordinate, stitched together from the individual milestone intervals. This is the MFPT/crossing-probability-based ("Hummer–Szabo-style") reconstruction referenced in the FFS pipeline notes — it does not require running additional simulations, only the trajectories already collected during FFS.

### Binning

Every continuous order-parameter value is mapped to a discrete bin with `binfinder`:

```
bin = floor(dir * (lambda - lambda0) / delT)
```

`dir` is +1 or -1 depending on which direction the milestones increase in, and `delT` is the bin width supplied at login (validated there to evenly divide every milestone interval). All of the downstream arrays are indexed by these bins, so results only make sense at the resolution of `delT`.

### Stage 1 — Basin statistics (`basindensity`)

Run once, on the basin-to-first-milestone trajectories (`filepaths[0]`). For each colvar file:

1. Tracks when the order parameter first crosses the basin boundary λ_B outward (the trajectory "leaves the basin").
2. From that point, accumulates a **density histogram** of visited bins between λ_B and λ_1 — when consecutive samples skip more than one bin, the count is smeared linearly across the skipped bins rather than assigned to a single one, so the histogram isn't sensitive to trajectory print stride.
3. Tracks the number of frames elapsed since leaving the basin, accumulated per bin, until the trajectory returns to λ_A (closing the excursion) — this becomes the basin's contribution to the **mean first-passage time (MFPT)** profile.
4. Both arrays are normalized by the number of basin-crossing trajectories observed.

### Stage 2 — Per-milestone statistics (`milestone`)

Run once per intermediate milestone. For each trajectory in that step's postprocessed directory:

- Trajectories that never actually pass through the `[λ_current, λ_next]` window (checked via their last recorded order-parameter value) are skipped.
- A trajectory is a **success** if its maximum order parameter reaches past λ_next, and a **failure** otherwise. Failures below λ_current are treated as basin returns and only contribute to failure-length bookkeeping; failures whose max lands between λ_current and λ_next contribute partial MFPT data up to where they turned around.
- A **density histogram** of visited bins is accumulated (same smearing rule as basin stage), plus a **success-count-weighted MFPT** at each bin — the number of frames since crossing λ_current, averaged only over trajectories that ultimately succeeded past that bin, with failures folding in extra path length.
- `totalsuccesses / tjCount` for that milestone is the local **crossing probability**: the fraction of trajectories launched at λ_current that reach λ_next.

### Stage 3 — Stitching it together (`FreeEnergyCalculation` main body)

Once every milestone has its local density and MFPT arrays:

1. **`cummprobs`** — the cumulative product of each milestone's local crossing probability, i.e. the standard FFS chain rule `P(λ_final | λ_A) = Π P(λ_{i+1} | λ_i)`. This is what converts "locally observed at this milestone" into "globally weighted across the whole run."
2. **`AllMFPT`** — the per-milestone MFPT arrays are spliced into one array spanning all bins, with each interval's contribution shifted by the accumulated MFPT of every interval before it (and rescaled by the ratio of total trajectories to successful ones), producing a single continuous mean-first-passage-time curve from the basin to the goal.
3. **`piListAll`** — an unnormalized stationary density across all bins, built by weighting each milestone's local density histogram by the cumulative crossing probability up to *that* milestone, then adding the basin's own density directly (the basin isn't down-weighted, since everything passes through it).
4. **`intPst`** — computed as a reverse cumulative sum of `piListAll`, then converted into a survival-style function: `intPst[j] = 1 - (normalized cumulative density up to j)`, i.e. "the probability of still being at or beyond bin j."
5. **`bFunc`** — computed per bin as `(intPst[j] - AllMFPT[j]/AllMFPT.back()) / piListAll[j]`. This combines the survival probability and normalized MFPT into a single function relating local density to global kinetics.
6. **`intOneOverbFunc`** — the cumulative sum (discretized integral) of `1/bFunc`.
7. **`FreeEnergy[j] = ln(bFunc[j]) - intOneOverbFunc[j]`** — the final free energy at each bin, in units of k_BT (no explicit temperature scaling is applied — the values are already dimensionless log-probabilities/MFPT ratios).

### Output

Written to the given `OutputName` as a tab-separated table, one row per bin, with columns for bin index, the corresponding λ value, `piListAll`, `AllMFPT` (raw and normalized), `intPst`, `bFunc`, `intOneOverbFunc`, `FreeEnergy`, and the per-milestone density contributions. A header line also records the cumulative crossing probability at each milestone. Note that `AllMFPT` is in **frame units**, not picoseconds — multiply by the trajectory print stride/Δt for absolute kinetic quantities.

## Landscape Variance (`LandscapeVariances`)

### What it does

Rather than reconstructing a free energy profile, this is a per-step diagnostic: for each FFS milestone step, it asks *how much does the observed transition probability vary across different starting configurations, and is that variance coming from run-to-run noise or from genuinely different configurations behaving differently?*

### Algorithm

For each step's postprocessed directory:

1. **`tallyfile`** parses `successes.txt` and `failures.txt`, extracting the originating structure ID from each trajectory's name (the `initialconfiguration_<ID>_...` token) and tallying success/failure counts per unique initial configuration (`Configstally`).
2. **`combineConfigVariance`** then computes, across all configurations `i` with `total_i` trials and local transition probability `p_i = successes_i / total_i`:
   - **Pooled transition probability** `P` — the trial-weighted average of all `p_i`.
   - **Within-configuration variance** — the average binomial variance `p_i(1-p_i)` per configuration, i.e. the noise expected from a finite number of trajectories even if the true `p_i` were identical everywhere.
   - **Between-configuration variance** — the trial-weighted squared deviation of each `p_i` from the pooled `P`, i.e. how much configurations genuinely differ from one another.
   - **Total pooled variance** is simply the sum of the two — a standard law-of-total-variance (one-way ANOVA-style) decomposition.
3. Two edge cases are handled directly instead of going through this decomposition: a step with only successes is `P = 1, Var = 0`; a step with only failures is flagged as an error (zero successes) and skipped, since there's nothing to build a landscape from.
4. A configuration with `P == 0` overall is marked **dead** — no trajectory from it ever succeeded at that step.

### Output

One file per step, named `<Outputname>_<step>.txt`, listing the source directory, number of unique initial configurations, total trajectory count, the pooled transition probability and variance, then a per-configuration breakdown (successes, failures, total, local `p_i`, deviation from `P`, and each configuration's contribution to the between/within variance terms).

### Why it's useful

A high between-configuration variance relative to within-configuration variance means the milestone's difficulty depends heavily on which structure you start from — a signal that more diverse initial configurations (rather than more trajectories per configuration) would improve sampling at that step. Configurations flagged dead are candidates for exclusion or re-seeding in the next FFS iteration.
